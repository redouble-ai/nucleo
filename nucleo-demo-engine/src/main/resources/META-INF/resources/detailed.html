Nucleo the runtime, demonstrated live documentation short page

Nucleo demo

This page is a live tour of Nucleo, the runtime for AI agents that live inside a Java application. Everything on it runs in this process, right now, against the models of your own account: nothing is mocked, every result is real, and every result shows what it cost.

The steps build on each other the way a real adoption would. Connect a provider and see which models your account can actually serve (1). Prove that one call works end to end (2). Watch an agent choose its own tools and skills (3). Fan a folder of documents out in parallel under a budget (4), search what was read by meaning (5), and turn it into a business answer where the model extracts facts and plain Java makes the decisions (6). Measure which model the job actually needs before paying for a bigger one (7). Then put a third kind of model to work, a decision model that never writes a word and only ranks options: run an agent on one (8), and hand it the one judgment in step 6 that is a verdict rather than a sentence (9). Along the way, the page shows the thing Nucleo exists for: model-driven work running as supervised, accounted, governed Jobs in an ordinary JVM.

1 Credentials and model catalog

Before you run anything, this panel shows what this process has to work with: which AI providers it can actually sign into, which models your account offers and at what price, and the catalog's order for each Grade of work, the models it prefers from first to last. Every step below runs on what this panel shows, which is why it comes first.

What to expect
  • GOODAt least one connection shows a credential, the banner is green and names your account's own models.json, and the Grades you plan to use are ordered.
  • NOTEEach Grade's rows are numbered in the order the runtime tries them. A bold number is a place you chose; an italic one is the runtime filling in by price. Drag a row, or use its arrows, to set the order.
  • NOTEEach Grade's header names the model that serves it now: for text, for a request with images, and for one with documents.
  • BADA red banner: the runtime fell back to the providers' shipped defaults, which know nothing of your account. Its instructions say how to fix it.
  • NOTEDimmed rows are models listed without a credential to call them; the runtime will never serve those.
  • TRYNo credential in the environment? Paste one into a connection card below - it is held in memory for this session only - then press Discover models to build the catalog and use it live.
What this demonstrates
  • Models are configuration, not code. Application code declares Grades of capability; which vendor and model serves each lives in models.json, discovered on the classpath the way logging configuration is, and owned by the deployment.
  • Swapping is an edit, not a migration. A model, or a whole provider, changes by editing that file: no recompile, and no vendor SDK types anywhere in application code.

2 Ask a quick question

Type a question and get an answer from a single model call. You choose a Grade of capability; the catalog decides which model that means. This is the quickest way to prove your credential, your catalog and a real model all work together.

What to expect
  • GOODAn answer in a few seconds, naming the model that gave it, for a fraction of a cent.
  • SLOWA half-minute run usually means the dispatcher is retrying an upstream 429 or 503 with backoff: a slower answer instead of an exception.
  • BADA refusal. A good refusal names exactly what to provide, a credential or a pin.
What this demonstrates
  • The call is a supervised Job. Admission reserves tokens against the model's rate limit before the request goes out, so throttling is capacity planning instead of a caught exception, and ten concurrent callers produce no retry storm.
  • The Grade dropdown is the whole model API surface. Code asks for a rung of capability; the catalog decides what serves it today, and may decide differently tomorrow with no code change.

3 Run the agent

This runs an agent - Nucleo calls it a Thinker. Instead of answering from memory, the model works in a loop: it plans, calls real Java Tools (this one carries tools that know today's date), and answers once it has what it needs. It also has a small Skill catalog it can draw on by itself: ask for something "briefly" and it will request the concise-answers Skill on its own. The run is drawn below as it happens: every turn the model takes, what it decided and what it cost, every Tool it called with the arguments it gave and the result it got back, the calls of one turn side by side because they run side by side. You choose the Grade the agent runs at, as in step 2: the agent declares MEDIUM, and a lower rung shows what a smaller model does with the same loop.

What to expect
  • GOODA one-line answer in five to fifteen seconds, with concise-answers under skills used and the date coming from a Tool call rather than the model's memory. The timeline shows two or three turns: the first admits the Skill and asks for the date, the last answers.
  • TRYRemove "briefly" from the query: a good run answers at length with an empty skill list, because the Skill is admitted by the model on demand. Then run the same query at MICRO: a small model often skips the Tool and guesses the date, and the timeline shows it, a turn with no Tool call under it.
  • BADA refusal naming a missing credential, or a Tool card that reads "failed" with the model never recovering in the next turn.
What this demonstrates
  • The loop is the runtime's. The while-loop most teams hand-roll around a chat API, with its JSON parsing, tool dispatch and error handling, ships as the Thinker base class; a malformed model answer goes back as an in-loop correction instead of an exception.
  • Tools are typed. Each is a Tool<I,O> class whose wire schema is generated from the POJOs; the model never sees hand-written JSON schemas drifting from the code.
  • Skills ship like dependencies. Prompt packages the model requests by name at runtime, versioned on the classpath, instead of string concatenation in code.
  • Every iteration is a Job under the same admission and budget as everything else in the process, and so is every Tool call and every model call: the timeline below is the runtime's own event stream, the same one a chat UI or a log observer reads, drawn as a tree by each job's parent.

4 Read a directory

Point this at a folder and it reads everything inside - code, PDFs, Office files, scans, images - storing every readable text in an in-memory index that steps 5 and 6 work from. Each file goes to the cheapest reader that can handle it:

  • Deterministic: plain code reads source, PDF text layers and Office files, at zero model cost.
  • Vision: a SMALL model reads scans and images. Each call declares what it sends, an image or a whole PDF, so it gets the first model of the SMALL order that accepts it.
  • Classifier: a SMALL model names the files whose bytes decide nothing.
  • Budget: a hard spend cap, enforced per call before the call; blank runs without one.
What to expect
  • GOODOn the shipped corpus: about 26 of 30 files read in seconds for a few cents, most rows DETERMINISTIC at zero model cost, the scanned letter and the screenshots read by the vision tier, and a few deliberately unreadable files SKIPPED with a note saying what a person would have to do.
  • TRYSet the budget to 0.01: the model-tier rows turn REFUSED at admission, before any money is spent, while code still reads what code can read.
  • BADEvery model-tier row FAILED points at the credential or the catalog, and each row's note says which.
What this demonstrates
  • Neither approach manages alone. Deterministic parsing is free and exact but cannot read a scanned letter; pushing all 30 files through a frontier model reads everything at a hundred times the price and answers slower. Routing each file to the cheapest capable tier is the shape of every document-ingestion pipeline.
  • Fan out without fear. The files run in parallel under admission control: tokens are reserved against each model's rate limit before the call, so 30 concurrent files produce zero 429s and no retry storm.
  • The cap acts before the money moves. Enforcement happens at admission, per call, mid-run: model calls the budget cannot cover never start, while the code-tier files keep flowing. A budget that reports after the invoice is a different, easier thing.
  • It is one page of Java. The orchestration is a Doer, plain fan-out code over Jobs, and every row reports the model it used and the cents it cost.

5 Search what was read

Ask a question about the files step 4 just read. The search works on meaning, not on words: your query goes through the same embeddings model that indexed the documents, and the documents closest in meaning win. It costs one embedding call - no model writes anything. Run step 4 first.

What to expect
  • GOODOn the shipped corpus: the headset-creak documents on top for the default query, even though no document contains "helmet" or "squeak". The match happens on meaning, and the top hit is the scanned letter, which only the vision tier could read into the index.
  • BADAn empty result on a corpus this small, or a refusal saying to run step 4 first.
What this demonstrates
  • One pinned embeddings model per corpus, frozen by the runtime. Vectors from two models are silently incomparable - the classic way a vector search degrades with no error to catch, usually months after someone "just upgraded the embeddings model". The runtime makes that mistake structurally impossible: the pinned choice holds for the life of the process.
  • Search rides the same rails as everything else. The embedding call is a Job: priced from the catalog, capped by the budget, attributed to its run.

6 Find the current prices

This digs through everything step 4 read and answers one business question: what does each product cost right now? A Doer - Nucleo's word for a fixed workflow that code, not a model, drives - runs it in three stages (run step 4 first; the budget works as there):

  • Extract (SMALL, parallel): every document read for the prices it states: who pays each, the dates attached, and the sentence it came from.
  • Group (MEDIUM, once): the distinct product names grouped into products.
  • Decide (plain Java): per product, audience and currency, prices compete by date as of the day you pick, and each lands as current, scheduled, superseded, confirmed or merely proposed. The day opens on 1 June 2026, when the last price the shipped corpus decides takes effect; move it back a month to watch that rise turn into a scheduled price, or clear it to answer for today.
What to expect
  • GOODOn the shipped corpus: about a minute, roughly a third of a dollar, a dozen products, and the Kestrel 1 gravel about twenty percent above its spring price, because meeting minutes dated only by their file name decided a raise and the arithmetic applied it to the price then in force. Every number expands to the quote that grounds it.
  • BADAn empty product list, refusals under a too-small budget, or prices with no source attached.
What this demonstrates
  • The model extracts facts; code makes decisions. Which of seven price statements is in force on a given date is arithmetic, and arithmetic inside a prompt is neither reliable nor auditable. Here it is a plain Java comparator you can unit-test.
  • Every conclusion keeps its evidence. Each price carries the source document and the sentence it came from, so a wrong answer is traceable instead of arguable.
  • Spend is shaped to the work. The cheap Grade fans out across 26 documents; one stronger call does the grouping.
  • The manual alternatives fail both ways. Nobody writes a regex for "raise both by 20% from June" buried in meeting minutes, and nobody should pay frontier prices per document to look for it.

7 Benchmark the agent

Would a cheaper model do this job just as well? The runtime's Benchmark takes the agent from step 3 and runs your query on every model your account can call, from MICRO to the strongest - the same agent, the same tools, the same query, only the model behind them differs. The strongest model answers first with the tools (the reference: the ground truth), then every other model races, and a judge compares each run - the tools it called, what they returned, its answer - against the reference under one rubric: 7 points for accuracy, 3 for shown work, a tool called wrongly or misread costing at least 3. Blind: the judge is never told which model ran.

What to expect
  • GOODA minute or two for two runs per model across the whole ladder and some tens of cents, then a table where the judge's column separates the models that called the date Tool and counted correctly from the ones that guessed, while the cost column shows a spread that is often tenfold for the same score.
  • GOODA cheaper model holding the reference's score is a pin candidate; the judge's per-run reasons sit under the table.
  • BADRows marked failed, whose messages name the cause, or an unjudged table because no model of the strongest Grade is callable.
What this demonstrates
  • Model selection as measurement rather than a default nobody revisits. Because code declares Grades and the catalog pins models, any workload wraps in a Benchmark unchanged.
  • One stick for every model. Each run gets a judge call of its own the moment it lands, comparing its full transcript against the reference's under the same spelled-out rubric, never carrying the model's name, so the judge cannot favor its own family - and a judge that fails costs only its own row's score.
  • Cost lands on the right run. The runtime attributes every call's tokens and cents to its run through Job lineage.
  • The race is watched, not waited for. Every run, every model call it makes and every judge is a Job on the runtime's message bus; the board below is those events streamed to this page as they happen, the same stream a chat renders, so you watch the whole ladder answer in parallel - queued, running, retrying, answered, judged - instead of a spinner.
  • Switching costs one line of models.json. Doing this by hand means one script per vendor and a spreadsheet; here the table is the evidence for that one edit.

8 Run an agent on a decision model

A decision model never writes a word: given a state and typed questions it returns a probability for every option and nothing else. Every agent framework you know assumes the model can call a tool and fill its arguments; this one cannot, and this step runs an agent on it anyway, the first agentic loop built for the model class. The runtime's decision thinker works an objective over three Tools that call no model at all: list a folder, read a file, split a document into its statements. Every turn, code works out the legal moves from the types and the model ranks them: which tool runs next, or finish; which of the files it should run on; and, for every statement produced so far, whether it belongs in the answer. The objective here is to find the statements in the shipped corpus that decide a change of a price. The model has to choose which of the thirty files are worth opening, when to stop, and which sentences answer, and nothing it says can be malformed, invented or out of bounds: every answer is a number over options code put in front of it. Every turn is drawn below as it happens: the state the model was shown, the distributions it answered, the tool that ran and what it produced. There is no reasoning to show, because none was produced; the distributions are its mind.

What to expect
  • GOODUnder half a minute on a Mac serving Kev-9B, a few seconds on a GPU, and no model cost at all when the model runs on your own machine. Four turns: the model lists the folder, opens the one file whose first words name a price (on the shipped corpus, the dealer portal changelog), splits it, finishes rather than reading on, and selects its April line about the Kestrel 1 prices, every other statement ranked well below it.
  • TRYOpen "what the model saw" under a turn: the objective, one line per artifact, the moves made; that is the whole of what the model decided on. Watch the argument bars on the read: thirty files ranked by a model that only saw each file's name, kind, size and first words. The minutes and the meeting notes, whose first words name a meeting and not a price, rank below the changelog, and the model finishes before opening them: a decision the record shows, made the way a person skimming names would.
  • BADA refusal naming a missing decision model (connect one in step 1), or a run that opens file after file until its turn budget ends it, with the selection then made from what was produced: a small model on a thin digest, and the record shows exactly where it wandered.
What this demonstrates
  • An agentic loop for a model that cannot call tools. A decision model has no way to name a tool or fill an argument; the decision thinker computes every legal move from the artifact types and asks the model only to rank them. The model never invents anything: what leaves the run is what tools produced, byte for byte.
  • Termination by construction. Each (tool, artifact) pair runs at most once, so the move set shrinks every turn and the loop ends on its own; a turn budget is the belt to that suspender.
  • The same door for a third kind of model. A decision entry sits in the catalog beside LLMs and embeddings, with its own pin, and every decision goes through admission (one request at a time on a Mac server, a quota window on a hosted one), is priced, metered and recorded like any model call. Nothing in the runtime was special-cased for it.
  • The record is the distributions. With no reasoning text, what the model thought is what it answered: every turn keeps every probability, on the thinker and on the job's record, so a run can be audited move by move.
  • A cheap orchestrator. A decision costs a few hundred input tokens at a fraction of an LLM's price, or nothing on your own machine, so the model that decides what deserves a paid call can afford to be asked on every turn.
  • Where it stops. A decision model reads a thin state and writes nothing, so it judges what code and tools produced and never extracts, drafts or computes; the runtime's decision documentation says which jobs belong to it and which to an LLM.

9 Find the current prices, grouped by a decision model

Step 6 again, with one tier swapped: the product names the documents used are grouped by a decision model instead of a MEDIUM model. The same documents, the same SMALL reading tier, the same plain-Java reconciliation, the same report, the same day to answer for (it opens on 1 June 2026, as step 6 does). Step 6 has two model judgments in it, and only one of them is a verdict: reading a document for the prices it states is writing, an LLM's work; deciding whether "Comet 2 city" and "Comet 2" are one product is a yes or no over two names code already has. That is a decision model's shape: a verdict per pair of names, "do these two mean the same product", with a calibrated probability each, then for every group of several names a choice of which is the product's proper name. Every name in the result is one the documents used; the model wrote none, and the pairing that costs a MEDIUM call in step 6 costs nothing here.

What to expect
  • GOODStep 6's table with the same prices, the grouping having cost no model money on a decision model served from your own machine, and some tens of seconds more on a Mac, one verdict per pair of names (a GPU is faster). The reading tier's spend is unchanged, since it is the same tier. The decision model tends to join names the MEDIUM model left apart, such as "Comet 2 city" with "Comet 2".
  • TRYCompare the products and their aliases with step 6's: where the two models draw the line between one product and two is the whole of the difference, and each run's reading tier names things a little differently, so run both twice.
  • BADA refusal naming a missing decision model (connect one in step 1 and press Discover), or an empty index (run step 4 first).
What this demonstrates
  • One workflow, a tier swapped by constructor. The Doer takes its two model-facing tools as constructors; nothing else in the pipeline knows which kind of model judged. A team can move a tier to a decision model the day it is good enough at that tier and keep everything downstream.
  • The judgment that fits the model. Pairing names is a yes-or-no question with a probability; that is what a decision model produces, and nothing it produces can be malformed or invented.
  • Under the same door. The two decisions are Jobs, priced from the catalog entry, admitted on the entry's own account, attributed to the run.
